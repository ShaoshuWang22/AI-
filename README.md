### 2. 正确的累计到达人数与五步漏斗转化率
#### 口径原理（快照逆向累加）
> 题目明确说明 CRM 数据为**期末截面快照**，商机只标记最后停留状态。销售漏斗遵循严格的单向递进关系：客户进入后续阶段的前提是必须经历此前所有阶段。
> 因此，某个阶段的**累计到达人数** = 当前停留在该阶段的人数 + 所有处于更高级阶段的人数 + 结案商机（赢单/丢单）。

#### 各阶段累计到达人数 & 五步逐级转化率（保留两位小数）
| 转化环节 | 累计到达人数 | 晋级/成交数 | 转化率 |
|---|---|---|---|
| 初步接触 → 需求确认 | 860 | 733 | 85.23% |
| 需求确认 → 方案演示 | 733 | 560 | 76.40% |
| 方案演示 → 商务谈判 | 560 | 432 | 77.14% |

### 3. 定位 Codex 首次引入核心口径错误的位置
- JSONL物理行号：**第 49 行（提交并执行脚本），第 50‑51 行打印输出**
- 对应动作：调用 bash 执行包含数据统计逻辑的 Python 脚本

**关键代码摘录（Codex 第 49 行）**
```python
n = {'初步接触': 127, '需求确认': 173, '方案演示': 128, '商务谈判': 88, '赢单': 215, '丢单': 129}
for a, b in [('初步接触', '需求确认'), ('需求确认', '方案演示'), ('方案演示', '商务谈判'), ('商务谈判', '赢单')]:
    x = n[b]
    N = n[b] + n[a]
    p = x / N
    ci = norm.interval(0.95, p, np.sqrt(p * (1 - p) / N))
    print(a, '->', b, x, N, p, ci)
```

**执行输出（Codex 第 50‑51 行）**
```
初步接触 -> 需求确认 173 300 0.5766666666666667 (0.5207, 0.6325)
需求确认 -> 方案演示 128 301 0.42524916943521596 (0.3693, 0.4810)
方案演示 -> 商务谈判 88 216 0.4074074074074074 (0.3418, 0.4729)
商务谈判 -> 赢单 215 303 0.7095709570957096 (0.6584, 0.7606)
```

**错误原因**
Codex 自行构造 `N = n[b] + n[a]` 作为各阶段转化的分母基数，逻辑存在根本性错误：
1. 将“初步接触→需求确认”基数算作300，完全丢掉方案演示(128)、商务谈判(88)、赢单(215)、丢单(129)合计560个商机；
2. 将期末停留截面直接等价于全生命周期流量，造成上游转化率严重低估（真实 85.23% 被错误算为 57.67%）。

### 2. 优劣势与风险分析
#### WorkBuddy
✅ **优势1：工程架构严密、中间态可审计**
以`results.json`和分步脚本为骨干，链路可追溯，具备工业级可审计能力。

✅ **优势2：深度自检与验证体系完备**
包含图表像素有效性校验、Word表格回读核对、Excel原始数据行数确认，多层质量防线。

⚠️ **风险1：上下文与工具调用开销较大**
多次细粒度诊断操作会带来更高Token消耗与运行耗时。

⚠️ **风险2：断言过严存在死循环风险**
自动化流水线中，严格文本匹配断言缺少容差，轻微非关键样式改动可能造成任务卡死。

#### Codex
✅ **优势1：端到端综合吞吐极高**
一次性完整大脚本，少量交互轮次即可输出结构完整、排版合规的Word文档。

✅ **优势2：快速推进目标能力强**
无大量中间断言阻拦，遇到非致命警告可快速降级绕行，推进阻力小。

⚠️ **风险1：盲目自信，缺少业务自省**
对截面快照这类特殊字段缺少主动求证，容易快速输出业务逻辑错误的数据。

⚠️ **风险2：形式检查掩盖内容缺陷**
依赖进程退出码、文件大小判断成功，缺少统计数字业务合理性交叉校验。

### 3. 针对 Codex 的三条具体 Harness 改进建议
#### 建议1：引入关键业务口径前置澄清与断言机制（Semantic Pre‑flight Check）
在Harness系统Prompt或任务模板中，针对漏斗、转化率、存量计算类统计任务，强制前置反思：
> 必须明确区分当前截面快照与全生命周期累计口径；必须校验漏斗各阶段总和与总样本商机数守恒。

#### 建议2：建立数据计算与排版渲染两阶段解耦规则（Compute‑Render Decoupling）
禁止Agent在同一个脚本同时完成统计计算 + Word/Excel文档生成。强制两步走：
1. 第一步：输出结构化统计指标字典并打印控制台；
2. 第二步：仅将已经验证过的数据填入模板完成渲染输出。

#### 建议3：增加交付物数值内容反向提取比对工具（Docx/Xlsx Content Diff Validator）
把验收逻辑从简单文件存在性、字数统计升级为内置内容比对器：
生成文档后自动解析表格，提取漏斗表、回归表等关键表格数值，与计算层源数据做Diff；发现不一致直接阻断交付。
